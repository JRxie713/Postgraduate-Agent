01工具选型：为什么用 Lighthouse

小组内通用、零侵入、可复现、可进 CI 的页面效率测试工具。

  • 通用性：免费开源，Chrome / Edge 均可驱动；Windows、macOS、Linux 同一套命令；无需在业务代码里埋点。
  • 指标标准：一次采集 FCP、LCP、TBT、CLS、SI、TTI，并给出资源体积、未使用 JS/CSS、缓存策略、渲染阻塞等审计项，可直接定位到文件。
  • 可归档、可对比：支持 JSON / HTML 双格式输出，适合做优化前后对比与答辩留档。
  • 可持续：CLI 形式便于接入 Lighthouse CI，对每次合并请求跑性能预算。

Lighthouse 通过 CHROME_PATH 指定本机 Chromium 内核浏览器（Chrome 或 Edge 均可，走同样的 DevTools 协议，口径一致）：

$env:CHROME_PATH="C:\Users\frola\AppData\Local\Google\Chrome\Application\chrome.exe"
npx lighthouse "http://127.0.0.1:4173/" --output=json --output-path="perf/final-mobile.json" --quiet
npx lighthouse "http://127.0.0.1:4173/" --preset=desktop --output=json --output-path="perf/final-desktop.json" --quiet
测试口径很关键：Lighthouse 必须跑生产构建产物。用 Vite 开发服务器测，得到的是“未打包 + HMR + 全量源码”的结果——实测开发服务器首屏 15 个请求 / 697 KB / TTI 5.2 s， 而同一页面生产构建仅 5 个请求 / 55 KB / TTI 1.4 s。开发服务器只用于开发，不用于性能验收。

03问题定位（实测 + 代码审查）

按影响面排序。P0/P1 为本次已修复项，P2 为已给出方案但未改动业务逻辑的项。

编号问题证据 / 根因状态
P0 首屏加载了全部页面代码 Lighthouse 未使用 JS 26 KiB；App.vue 静态 import HomeView，HomeView 又静态 import 870+ 行的 FileTransferView，导致登录页必须下载工作台和文件传输页的逻辑。 已修复
P0 CSS 未按页面拆分 单个 23.90 kB CSS（gzip 5.18 kB）进入首屏阻塞链，其中登录页用不到的样式占大头：首屏唯一的渲染阻塞资源就是这份 CSS。 已修复
P1 第三方库与业务代码同包 Vue 运行时与业务代码打进同一 chunk，任何业务改动都会让 74 kB 的 vue 代码缓存失效。 已修复
P1 静态资源没有利用长效缓存 实测响应头 Cache-Control: no-cache；文件名已带 hash，却仍要求每次访问重新校验，重复访问和 CDN 命中率受损。 已给部署方案
P1 压缩策略未落到部署配置 preview 自带 gzip；仓库里没有正式环境的压缩配置，换机器部署容易退化为明文传输。 已给部署方案
P1 文件分片进度高频重算 updateBigPercent() 在每次 XHR progress 里遍历全部分片（1 GB 文件 512 片、每片多次回调），是 O(片数 × 回调次数) 的重复计算。 已修复
P2 交互后全量重拉数据 勾选任务、增删任务/计划都会重新请求整份计划列表；用户分页、政策列表同理，属于可避免的往返。 已给方案
P2 额外图标请求 默认 favicon 单独发一次 1.1 kB 请求。 已修复
P2 大文件分片网格 DOM 线性增长 每个分片渲染一个状态格；超大文件（上千片）时节点数偏多，建议窗口化渲染。 已给方案

附：Lighthouse 还报告了非性能项（颜色对比度、缺少 main landmark、缺少 meta description、robots.txt 被 SPA 回退命中）。它们不影响页面效率，列为可选优化，未在本次改动。

04已落地的优化

所有方案均已在代码中生效，并完成生产构建与 Lighthouse 复测（2026-11-26 复核结果见 5.1）。

4.1 登录首屏与工作台按需加载（代码分割）

frontend/src/App.vue：HomeView 改为 defineAsyncComponent，并用 Suspense 提供加载态兜底，登录页不再携带工作台代码。

frontend/src/views/HomeView.vue：FileTransferView 同样改为异步组件，只有切到“文件传输”tab 时才下载。

// App.vue
const HomeView = defineAsyncComponent(() => import('./views/HomeView.vue'))

// HomeView.vue
const FileTransferView = defineAsyncComponent(() => import('./FileTransferView.vue'))

4.2 第三方库独立分包

frontend/vite.config.js：把 vue 拆成独立 vendor chunk，业务代码更新时仍能命中 vue 的长效缓存；Vite 会自动在 HTML 注入 modulepreload，不产生额外瀑布。

build: {
  rollupOptions: {
    output: {
      manualChunks: { vue: ['vue'] }
    }
  }
}

4.3 消除图标请求

frontend/index.html：favicon 改为内联 SVG data URI，省掉一次额外请求，同时替换掉默认的 Vite 图标。

4.4 分片进度按帧合并

frontend/src/views/FileTransferView.vue：updateBigPercent() 用 requestAnimationFrame 合并，同一帧内多次进度回调只重算一次，大文件时不再重复遍历整张分片表。

4.5 生产产物本地测试通道

frontend/vite.config.js 增加 preview.proxy，让 npm run preview 也能把 /api 代理到 8080，团队可以直接用真实产物复现本报告的数据。

07部署侧配置示例（缓存 + 压缩）

解决“hash 文件名却 no-cache”“没有压缩配置”两个问题。按实际部署方式选用。

server {
  root /var/www/kaoyan;          # 指向 frontend/dist

  # 带 hash 的静态资源：一年长效缓存，且不再回源校验
  location /assets/ {
    add_header Cache-Control "public, max-age=31536000, immutable";
  }

  # 入口 HTML 必须实时校验，保证发版后立刻拿到新的资源引用
  location = /index.html {
    add_header Cache-Control "no-cache";
  }

  # 压缩
  gzip on;
  gzip_comp_level 6;
  gzip_min_length 1024;
  gzip_types text/css application/javascript application/json image/svg+xml;
  # 安装了 brotli 模块时优先使用：
  # brotli on;
  # brotli_comp_level 5;
  # brotli_types text/css application/javascript application/json image/svg+xml;

  location /api/ {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host $host;
  }

  location / {
    try_files $uri $uri/ /index.html;
  }
}

09结论

  • Lighthouse 作为小组通用页面效率测试工具，能在不做任何代码改造的前提下给出可定位、可对比、可进 CI 的结论；关键是必须测生产构建产物。
  • 本项目的核心问题是“单包首屏”：登录页被迫下载工作台与 870+ 行文件传输页的代码和样式。通过异步组件拆分、vendor 分包、CSS 分割后，首屏 gzip 从 48.55 KB 降到 37.08 KB（-23.6%），未使用 JS 从 26 KiB 降到 0。
  • 剩余收益在部署侧：静态资源长效缓存与 brotli/gzip 压缩，按第 7 节配置后重复访问与弱网首屏还能继续改善。
  • 面向后续迭代，建议把 Lighthouse CI 与性能预算纳入合并流程，避免新页面再次把首屏体积推高。
